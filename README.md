# Liberty MMORPG

Браузерная MMORPG внутри Telegram. Сервер — Node + PostgreSQL, клиент — canvas.

Боевая версия крутится на дроплете из ветки **`postgres-migration`**. Это и есть
ветка по умолчанию. Ветка `main` осталась от версии на MongoDB, она больше не
запускается — не берите её за основу.

---

## С чего начать

```bash
git clone https://github.com/libmmorpgbot/libmmorpgbot-.git
cd libmmorpgbot-
npm install
```

`.env` в репозитории **нет и не будет** — там пароль к базе, токен бота и ключ
админки. Его выдаёт владелец отдельно. Обязательный минимум, чтобы сервер
поднялся:

| переменная | зачем |
|---|---|
| `DATABASE_URL` | подключение к PostgreSQL |
| `PG_CA_FILE` | сертификат к ней |
| `TG_BOT_TOKEN` | бот, через которого заходят игроки |
| `ADMIN_PASSWORD_HASH`, `ADMIN_TOKEN_SECRET` | вход в админку |

Запуск: `npm start` (или `npm run dev` под nodemon).

`dotenv` в зависимостях нет — сервер читает только то, что уже есть в
окружении. Локально файл надо внести в него самому:

```bash
set -a; . .env; set +a
npm start
```

### Где переменные лежат и как их менять

| где | что |
|---|---|
| локально | `.env` в корне репозитория. В git его нет и не будет (`.gitignore`) |
| на дроплете | `/srv/liberty/env` — обычные строки `КЛЮЧ=значение`, по одной |

На сервере файл читает не приложение, а systemd — через `EnvironmentFile=` в
юните `liberty-next`. Из этого следует главное: **правка подхватывается только
перезапуском**, `systemctl reload` окружение не перечитывает.

```bash
nano /srv/liberty/env            # поправить
systemctl restart liberty-next   # применить
curl -s localhost:3000/health    # убедиться, что поднялся
```

Одну переменную безопаснее менять не редактором, а так — иначе легко оставить
в файле две строки с одним ключом, и победит последняя:

```bash
sed -i '/^TG_BOT_TOKEN=/d' /srv/liberty/env
echo "TG_BOT_TOKEN=..." >> /srv/liberty/env
```

**Значение с `$` или пробелом обязано быть в одинарных кавычках.** systemd не
раскрывает переменные, а вот человек, который сделает `. /srv/liberty/env`,
чтобы запустить проверку руками, — раскроет. На этом уже горели:
`ADMIN_PASSWORD_HASH` это `scrypt$16384$8$1$…`, и от 127 символов оставалось
десять — `scrypt6384`. Симптом был один: верный пароль не подходит. Проверить и
починить разом (идемпотентно, уже закавыченное не трогает):

```bash
node /srv/liberty/next/dev/env-quote.js /srv/liberty/env
```

Две переменные руками не трогают:

* `BUILD_COMMIT` — её ведёт сама выкладка, по ней `/health` отвечает, какая
  сборка в игре. Правка вручную соврёт про то, что реально запущено.
* `ADMIN_URL` — её там нет намеренно, см. «Миграции базы» ниже.

Чего в репозитории нет и стоит помнить: **юнит `liberty-next.service` живёт
только на сервере**. То есть `EnvironmentFile`, лимиты и порядок запуска
существуют в одном экземпляре и не восстановятся из git — ровно та беда, от
которой уходит `dev/server-deploy.sh`.

## Правила, которые дороже всего стоили

Они здесь не для порядка — каждое написано после поломки на живых игроках.

**Клиент — это один общий scope.** `server/bundle-files.js` склеивает 25 файлов
из `js/` в один скрипт. Объявили `const` с именем, которое уже есть в
`shared/definitions.js` (а он идёт первым) — это SyntaxError, и у всех игроков
чёрный экран. Не «сломается эта функция», а не запустится вообще ничего.

**Проверки ходят по БОЕВОЙ базе.** Отдельной тестовой базы у проекта нет.
`dev/all-checks.sh` создаёт себе игроков и убирает их за собой в конце. Если
прервать прогон на середине — мусорные аккаунты останутся в рейтинге и в чате.
Подчистить: `node dev/purge-test-accounts.js --apply`.

**Проверка, которая ничего не напечатала, считается УПАВШЕЙ.** Не
«пропущенной». Однажды пять проверок падали до первой строки вывода, и молчание
полгода читалось как «просто не запускал».

**`git stash` — запрещён.** Один раз им проглотило работу целого дня.

**Порядок блокировок в Postgres.** `items.lockPlayer` должен быть ПЕРВЫМ
запросом любой транзакции, которая что-то меняет. Иначе дедлоки под нагрузкой.

**У `liberty_app` намеренно нет права DELETE на `ledger`.** Процесс, который
двигает деньги, не должен уметь стирать запись об этом. Это не недосмотр
доступов, не выдавайте это право.

## Проверки

```bash
bash dev/all-checks.sh
```

Шестьдесят с лишним групп в трёх ярусах: без базы / с базой / с живым сервером.
Гонять перед каждым деплоем. Каждая проверка запускается и отдельно:
`node dev/spawn-check.js`.

Новая проверка чего-то стоит только если её сначала показали КРАСНОЙ на сломанном
коде. Проверка, которую никогда не видели падающей, не проверяет ничего.

## Деплой

Выкладка идёт **через GitHub, а не мимо него**. Порядок важен механически:
коммит уезжает в репозиторий, и только если это удалось, сервер выкладывает
именно его. Выложить код, которого нет в репозитории, невозможно.

```bash
bash dev/deploy.sh
```

Что он делает: требует чистого дерева → `push` в GitHub (не удалось — выкладки
нет) → довозит коммит до сервера → обновляет `pgtest`, на котором гоняются
проверки → **холостой прогон** (собирается ли клиент, на месте ли симлинки —
всё это до перезапуска, то есть не выгоняя игроков) → **накатывает миграции**
→ выкладка с проверкой, что игра ответила и назвала тот самый коммит. Не
ответила за 25 с — откат.

### Миграции базы

Катаются сами, на каждой выкладке, до перезапуска. Отдельно ничего запускать
не надо.

`server/db/migrate.sh` идемпотентен: применённое пропускает, новое применяет
атомарно — файл и запись о нём в одной транзакции, так что упавшая миграция не
оставляет следов. Не прошла — выкладка отменяется целиком, игра остаётся на
прежней сборке и прежней схеме.

Запускается **всегда**, а не «если в выкладке новый файл»: применена ли
прошлая, знает база, а не код. Именно так и вышло однажды — код с новой
колонкой выложили, миграцию накатить забыли, и игроки получили «Ошибка
сервера» вместо новой возможности.

Одно правило скрипт соблюсти не может, и оно на авторе миграции: **миграция
обязана быть добавляющей**. Между накатом и перезапуском несколько секунд
работает старый код; новая колонка ему не мешает, переименованная — ломает
сразу. Переименования и удаления катятся в два захода: сперва добавить и
выложить, потом отдельной выкладкой убрать лишнее.

Руками — если понадобится накатить, не выкладывая:

```bash
ssh root@178.128.136.68
bash /srv/liberty/next/dev/migrate-now.sh
```

Он спросит пароль `doadmin` (DigitalOcean → Databases → liberty-db →
Connection details), вводится вслепую и на диск не пишется. Дальше сам: строит
индексы, которым нужен `CONCURRENTLY` (миграцией их не создать —
`--single-transaction`), накатывает миграции, показывает, что схема на месте,
и перезапускает сервер.

Именно поэтому `ADMIN_URL` в `/srv/liberty/env` не лежит. А чтобы выкладка при
этом не отказывалась работать после ручного наката, она спрашивает базу —
применена ли миграция, — а не сравнивает файлы. Разовая выкладка с миграцией,
если понадобится, делается так и ничего не оставляет на диске:

```bash
ADMIN_URL='postgres://doadmin:…' bash /srv/liberty/deploy.sh
```

### Кнопкой, с телефона

В телеграм-админке: **`/admin` → 🚀 Выкладка**. Экран показывает, что сейчас
в игре и что в GitHub, сколько новых коммитов и какой последний. Одна кнопка —
и через полминуты в тот же чат придёт сообщение: выложилось или не поднялось и
откатилось.

Ssh для этого не нужен. Источник тот же и единственный — GitHub.

### Из консоли

Выкладка не привязана к одной машине. То же самое с сервера:

```bash
ssh root@178.128.136.68 'bash /srv/liberty/deploy.sh'
```

`--dry-run` проверяет коммит, не трогая игру. Аргументом можно назвать коммит —
это откат: `bash /srv/liberty/deploy.sh 4ec695a`.

Что сейчас в игре, что в GitHub, что у вас — и совпадает ли:

```bash
bash dev/status.sh
```

На время работ игру закрывают флагом `/srv/liberty/maintenance.on` — он
переживает рестарты и сам гаснет через сутки.

### Проверки на GitHub

На каждый push прогоняется первый ярус `all-checks.sh` — тот, которому нужен
один node. **Зелёная галочка не значит «проверено»**: база лежит внутри
частной сети DigitalOcean и снаружи недостижима, поэтому ярусы с базой и с
живым сервером остаются обязательными на дроплете перед выкладкой.

## Где что лежит

| | |
|---|---|
| `server/game/Room.js` | бой, урон, смерть, спавн — сервер здесь главный |
| `shared/definitions.js` | предметы, классы, дропы. Общий для клиента и сервера |
| `server/db/repos/` | вся работа с базой, по одному файлу на область |
| `server/handlers2/` | обработчики сокетных сообщений |
| `js/` | клиент |
| `dev/` | проверки и скрипты выкладки |

Учтите: `dev/README.md` описывает старую версию на MongoDB и врёт про
`npm run dev:local`. Не переписал его, чтобы не выдавать за проверенное то,
чего не проверял.
