# Локальный запуск (без боевой базы)

```bash
npm install          # один раз; подтянет mongod для mongodb-memory-server (~200 МБ)
npm run dev:local
```

Скрипт поднимает собственный mongod, наполняет его тестовыми аккаунтами и
запускает **тот же** `server/index.js`, что и на проде — просто указывает его на
базу, которую никто больше не видит. Боевая база недостижима в принципе: URI
генерируется на месте, а на не-localhost адрес лаунчер запускаться отказывается.

В консоли появятся ссылки:

```
  http://localhost:3000/?dev=dev     чистый аккаунт — попадает на экран выбора класса
  http://localhost:3000/?dev=hero    Танк 24 ур., экипировка, 12k золота, Liberty/GRAM, лидер клана
  http://localhost:3000/?dev=rival   Егерь 18 ур., в клане, выставил лоты на рынке
  http://localhost:3000/admin.html   админка, admin / admin
```

Любое другое имя (`?dev=whatever`) — новый аккаунт; id выводится из имени, так
что при следующем запуске это будет тот же персонаж.

## Флаги

| | |
|---|---|
| `npm run dev:local` | база в памяти, стирается при выходе |
| `... -- --persist` | база в `.dev-mongo/`, переживает перезапуск (нужно, когда тестируешь сохранения) |
| `... -- --reseed` | пересобрать тестовые аккаунты (с `--persist` — затирает то, что было) |
| `... -- --port 4000` | другой порт |
| `... -- --uri mongodb://localhost:27017/x` | свой локальный mongo (docker) вместо встроенного |

Сид лежит в `dev/seed.js` — правится как обычные данные: игроки, клан, лоты на
рынке, спецквесты. Повторный запуск с непустой базой сид пропускает.

## Как работает вход

Игра логинится через Telegram Mini App initData, которого в обычном браузере
нет. Обхода авторизации в сервере не появилось: при `DEV_LOCAL=1` (его ставит
только `dev/local.js`) поднимается маршрут `/dev/init-data`, который **подписывает
настоящий initData** тем же HMAC, что и Telegram, локальным dev-токеном — а
дальше клиент идёт по обычному `loginTelegramWebApp`. На проде маршрута нет
вовсе, и подпись dev-токеном там всё равно не прошла бы проверку.

Клиентская половина — в `_initTelegramWidget` (`js/network.js`): на `localhost`
он сначала пробует `/dev/init-data`, и только если маршрута нет, показывает
привычное «Доступно только в Telegram».

## Что ещё меняется в dev-режиме

- Telegram-поллинг (`getUpdates`) не запускается — с фиктивным токеном он всё
  равно может только получать 404 раз в полсекунды.
- Уведомления боту (новый игрок, заявки на депозит) уходят в никуда — бота нет.
- `socket.io` клиент грузится с CDN, но если CDN недоступен (офлайн), страница
  подхватывает копию, которую раздаёт сам сервер.

## Замеры производительности

Три инструмента для проверки латентности и ёмкости сервера. Все работают против
локального сервера из `dev/local.js` и на прод не влияют. Выводы, полученные с
их помощью, — в `AUDIT-PERF.md`.

```bash
npm run dev:local            # в другом терминале

node dev/loadtest.js 150 40 hub     # 150 ботов, 40 с, толпа в хабе
node dev/roombench.js 300 400 arm   # тик мира в изоляции: 300 игроков, 400 тиков
```

`dev/loadtest.js` — синтетические клиенты: логинятся через `/dev/init-data`,
выбирают класс, ходят, бьют мобов и меряют RTT. Печатает перцентили RTT, худших
ботов, темп и объём потока `gameState`. Поведение настраивается переменными
окружения (`MOVE_HZ`, `ATTACK`, `PROJ`, `MAPVIEW`, `STAGGER`, `TAG`) — каждая
изолирует одну статью расходов, см. шапку файла. Например
`STAGGER=0 node dev/loadtest.js 150 30 hub` воспроизводит наплыв переподключений
после рестарта, а `PROJ=2 ...` — рассылку визуалов боя всему этажу.

`dev/roombench.js` — `Room._tick()` без сокетов и без базы: перцентили времени
тика отдельно для кастовых (с рассылкой) и остальных. Раскладка выбирает и
**этаж**, а не только позиции: `hub` и `spread` — хаб (мобов там нет вообще),
`arm` — настоящий этаж рукава, толпа стоит в гуще мобов и ИИ работает.

`dev/egress.js` — во что обходится один игрок в байтах: поднимает сервер,
грузит настоящий клиент в Chromium и считает всё, что ушло наружу — HTTP по
типам и отдельно websocket-поток уже в мире. Две цифры разной природы:
первая загрузка платится один раз на новое устройство (ассеты отдаются
`immutable`), поток — за каждую секунду игры. Когда счёт за хостинг упирается
в egress, этот скрипт говорит, за какой из двух идти.

`dev/profsum.js` — сводка CPU-профиля по собственному времени функций:

```bash
node --cpu-prof --cpu-prof-dir=./prof dev/local.js
node dev/profsum.js prof/CPU.*.cpuprofile 30
```

Тайминги тика живого сервера отдаёт `/health` — но только админу и обнуляя окно
при каждом чтении. Сам по себе `/health` — это **liveness**: 200, пока жив
процесс, независимо от состояния Mongo (см. SCALING.md — 503 оттуда за
перезапускающим healthcheck'ом убивал сервер на каждом блипе базы).
Готовность базы отдаёт `/health/ready` (503 при обрыве) — на него вешают
дашборды, но не перезапуск. Строка по этажу 11 (Страх) сводная: `instances` —
сколько приватных комнат сейчас крутится.

```bash
TOKEN=$(curl -s -X POST localhost:3000/admin/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin"}' | sed 's/.*"token":"\([^"]*\)".*/\1/')
curl -s localhost:3000/health -H "Authorization: Bearer $TOKEN"
```

### Проверки после оптимизаций

```bash
node dev/fanout-check.js     # снаряды: сосед видит, дальний — нет
CHROMIUM_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome \
  node dev/smoke.js hero     # реальный клиент в браузере + переподключение
```

`dev/fanout-check.js` сторожит рассылку боевых визуалов по радиусу
(`_emitNearby`): три клиента, один стреляет, соседний обязан получить всё,
дальний — ничего. Падает, если оптимизация начнёт «съедать» чужие эффекты.

`dev/smoke.js` поднимает настоящий клиент в headless-браузере: логин, выбор
класса, движение, затем принудительное переподключение — и проверяет, что мир
на месте, а карта **не** скачивается заново (`refetchedMap: 0`). Пишет скриншот
(`SHOT=путь.png`) и выходит с ненулевым кодом, если клиент не доехал до игры.
`CHROMIUM_PATH` нужен там, где браузер лежит не по версионному пути Playwright.

### Рисует ли клиент вообще

```bash
node dev/render-check.js              # затем открыть http://127.0.0.1:8791/render-check
MIN=1 node dev/render-check.js        # то же, но минифицированным бандлом — тем, что едет игрокам
```

Единственная проверка в `dev/`, которая **видит экран**. Все остальные читают
код или спрашивают базу — а однажды дубль верхнеуровневого `let` между
`js/game.js` и `js/pixi-world.js` уехал в прод и оставил всех игроков с пустой
страницей: бандл прекрасно разбирался на сервере, просто никто его не запускал.

Поднимает настоящий `index.html` с настоящим бандлом (заглушены ровно две вещи:
`socket.io` и Telegram SDK), подделывает этаж, персонажа и по одному экземпляру
всего, что мир умеет рисовать, гоняет настоящую пару `update()`/`render()` —
и считает **реальные вызовы `gl.drawElements`/`drawArrays`**, а не доверяет
графу сцены на слово. Ни сервера, ни базы, ни логина не нужно.

Кадры прогоняются напрямую, а не через `requestAnimationFrame`: rAF — это
колбэк вертикальной синхронизации, и браузер, который страницу не композитит
(фоновая вкладка, headless), не вызовет его никогда. Заодно тайминг меряет
работу, а не монитор.

Что сторожит, кроме «не упало»:

- **число draw call'ов** — должно оставаться примерно плоским, сколько бы
  мобов, игроков и частиц ни добавилось. Растёт — значит батчинг сломался.
- **цена одного объекта в вершинах**. Спрайт из пула — один квад, шесть
  индексов; `Graphics.drawCircle` — около девяноста четырёх, потому что PixiJS
  тесселирует круг в JavaScript и заново заливает буфер каждый кадр. Частицы,
  лут и снаряды когда-то были кругами. Считается на объект, а не в сумме, и
  требует, чтобы геометрия была **больше нуля** — иначе «дёшево» и «ничего не
  нарисовалось» дают одинаковый ответ, а второе выглядит как доказательство.
- **задел подгрузки тайлов**: у чанков, построенных вперёд и ещё ни разу не
  показанных, текстура обязана уже лежать на видеокарте. Скрытый спрайт PixiJS
  пропускает целиком, так что заливка приходилась ровно на кадр показа — тот
  самый, который задел и должен был защитить.
- **атлас цифр урона** — одна страница (иначе цифры перестают быть одним
  draw call'ом) и кириллицы в нём нет: локализованные всплывашки должны честно
  падать обратно на `PIXI.Text`, потому что глиф, которого в атласе нет,
  рисуется как **ничто**, молча.

Оставляет после себя `dev/_render-shot.png` — склеенный кадр мира и HUD.
«Нарисовало что-то» и «нарисовало то, что надо» — разные утверждения, и на
второе assert'ом не ответишь.

### Гонки вокруг предметного ценза

```bash
node dev/storage-race-check.js   # ни сервера, ни базы не нужно
```

Сторожит правило «предметный ценз считает inventory + equipment + storage как
одно целое» (`_itemCensus`) против защиты от устаревшего сейва в `saveProgress`.
Перекладывание в хранилище — клиентское и доезжает только со следующим сейвом, а
`_invRev` двигает **любая** серверная выдача предмета; если выдача попадает в это
окно, сейв приходит устаревшим. Пока защита подменяла серверной копией только
`inventory`, блоб описывал сразу два момента времени: положил вещь — она
считалась дважды (ценз сносил игроку весь набор предметов и писал его в лог как
`save_items_forged`), забрал — не считалась нигде, а ценз ловит только рост, так
что сейв принимался и **вещь исчезала навсегда**.

Вторая гонка того же ценза — рынок. Выставление лота оптимистично вырезает
предмет из локального инвентаря, а сервер создаёт лот и сохраняет удаление
**до** того, как ответит. Поэтому обрыв связи в этом round-trip ничего не говорит
о том, доехал запрос или нет — а клиент раньше считал, что не доехал, и возвращал
предмет себе. Когда догадка была неверной, предмет существовал сразу и в
инвентаре, и живым лотом, пока ценз не сносил игроку весь набор как поддельный.
Теперь клиент
не гадает, а `selectChar` при расхождении досылает авторитетный `inventorySync` —
и он же чинит обратный случай, когда запрос действительно не доехал.

Тест вырезает настоящие `_itemCensus` / `_censusOverflow` / `_censusEqual` /
`_canonSavedItem` и сам блок защиты прямо из `server/index.js` (срезом по
исходнику, не копией) и прогоняет их в `vm` на настоящем каталоге предметов —
так что переименование или правка в бою ломает проверку, а не проходит мимо неё.

Он же сторожит два флага, которые клиент выставлял себе сам из консоли:
`playerInvis` (мобы переставали видеть игрока навсегда — при том, что инвиз в
игре не выдаёт ни один навык) и потолки `statsUpdate`. Последние проверяются не
на «какое-то число», а на то, что каждый укладывается между реальным максимумом
стакающихся баффов из `recompute()` и +12% сверху: одного общего ×3 хватало,
чтобы подделанный пакет навсегда сел на тройную атаку без единого живого баффа.

### Уровень и опыт

```bash
node dev/xp-ledger-check.js   # ни сервера, ни базы не нужно
```

Уровень — самое ценное, о чём клиент может соврать: из него выводятся
`baseAtk/baseDef/baseMaxHp` (санитайзер пересчитывает их именно поэтому) и бюджет
очков апгрейда. Раньше он приезжал из сейва с единственным ограничением —
потолком 1000, при контенте до `MAX_MONSTER_LEVEL` 78.

Золоту нужен рейт-кап, потому что сервер не видит событий, которые его приносят.
С опытом иначе: сервер сам считает каждое очко, которое выдаёт (`xpAtLevel` в
`Room.attackEnemy`, награды за квесты), поэтому он не гадает скорость, а
**считает** — и сравнивает суммарный опыт за всю жизнь персонажа (`xpTotalAt`,
`shared/definitions.js`). Каждая выдача кладётся в счёт по самому щедрому
множителю, который клиент мог бы к ней применить (клан ×1.20 + зелье ×2, в том же
порядке и с тем же округлением), поэтому честного игрока это не задевает.

Тест проверяет обе половины: что подделка не выживает и что **честный игрок
никогда не срезается**. Вторая половина важнее — она уже поймала реальную ошибку:
клиент округляет после кланового бонуса и удваивает после, так что на низких
уровнях округление вверх пробивало плоский ×2.4 и резало свежего персонажа.
Отдельный свип на 5600 сценариев (уровни, мобы, размер пати, клан, зелье, Страх)
гоняется тем же способом.

### Потери предметов

```bash
node dev/item-loss-check.js   # ни сервера, ни базы не нужно
```

Сторожит исправления из `BUG_AUDIT.md`. У всех находок была одна форма: хендлер
списывал предмет — или брал за него деньги — и **только потом** выяснял, что
класть его некуда, когда лот уже снят, GRAM уже потрачены, а стак уже вырезан.

Главное, что здесь закреплено:

* **Стак нельзя считать по наличию поля `slot`.** `isStackableItem` смотрит
  только на `it.slot`, поэтому объект вида `{ id, qty }` читался как
  нестакающийся и `_invRemove` вырезал запись целиком: депозит 5 осколков в
  клановое хранилище удалял стак из 5000. Теперь слот доопределяется по каталогу
  (`_itemSlotOf`), и тест проверяет именно это — что «голый» `{ id, qty: 5 }`
  оставляет 4995, а не ноль.
* **«Есть ли место?» обязано отвечать так же, как ведёт себя `_invAdd`.** Старая
  проверка `!isStackableItem(item) && полон` пропускала стакающийся предмет, у
  которого стака ещё нет, — и `_invAdd` отказывал уже после оплаты. Тест гоняет
  `_invHasRoomFor` и `_invAdd` на одних и тех же четырёх случаях и требует
  одинакового ответа.
* **Разрушающее действие адресуется предметом, а не номером слота.** Индексы
  клиента и сервера расходятся после любого серверного `splice` до прихода
  `inventorySync`, и сжигание принимает любую редкость — то есть по устаревшему
  индексу сгорала не та вещь. Теперь запрос несёт `id` (+ `enhance` для шмота), а
  индекс — только подсказка.
* **Поля сейва, которые раньше проезжали нетронутыми** (`potionBag`,
  `skillLevels`, `advSkill*`, `buffs`, `type`, `hudPotion`), теперь ограничены по
  форме и значениям. `potionBag` — с зубами: `usePotion` списывает зелья именно
  из этой копии.

Функции вырезаются из настоящего `server/index.js` срезом по исходнику (как в
`storage-race-check.js` и `xp-ledger-check.js`) и прогоняются в `vm` на живом
каталоге предметов, а фикстуры (`UNIQUE_SHARDS[0]`, первое оружие из `ITEM_DEF`)
берутся оттуда же — так что переименование в каталоге роняет тест, а не проходит
мимо него.

### Что реально едет по сокету

```bash
node dev/netprobe.js 20 20 hub      # 20 соседей, 20 секунд, толпа
PROJ=0 node dev/netprobe.js 20 15 hub
MAPVIEW=1 node dev/netprobe.js 20 15 hub
```

`dev/netprobe.js` ставит один инструментированный клиент внутрь толпы обычных
ботов и печатает его трафик с разбивкой по событиям в обе стороны: сколько раз
в секунду, сколько байт, средний размер пакета, плюс кадры engine.io под ними
(бинарное событие socket.io — это два кадра: JSON-конверт и вложение, их доля в
выводе — `framingOverheadPct`). Внизу — расход в мегабайтах за час игры.
На этих цифрах построен `AUDIT-NET.md`.

### Плавность чужих игроков

```bash
node dev/snapshot-check.js 20          # MOVE_HZ=15|20|30|40
```

Один бот бегает по кругу, другой смотрит на него через мировой поток и считает
снапшоты, повторившие предыдущую позицию. Каждый такой повтор — 50 мс, в
которые интерполяции у получателя некуда двигаться: на экране чужой персонаж
стоит кадр и прыгает на следующем, а беговая анимация начинается заново.
Появляются они, когда клиент шлёт позицию не чаще, чем сервер рассылает мир
(20 Гц). Именно этим обернулась первая версия N3 — подробности в `AUDIT-NET.md`.

`dev/remote-motion-check.js` — та же проверка через настоящий клиент в браузере
(facing, флаг движения, ключ анимации по кадрам). В headless без GPU браузер
даёт ~16 fps, поэтому для оценки плавности он ненадёжен — держится как
диагностика на машине с нормальной графикой.

## Тести і зовнішній світ

Будь-який тест, який кличе `app.boot()`, запускає воркери. Воркери довго
опитують `getUpdates` опс-бота і сканують гаманець. Telegram дозволяє **одного**
читача на токен, тож другий опитувач забирає в живого сервера кнопки виведення.

Шлюз — `OPS_LIVE`. Він закритий за замовчуванням і відкривається тільки при
`OPS_LIVE=1` або `NODE_ENV=production`.

`dev/sync.sh` підвантажує бойовий env (там адреса бази і CA — другої копії
навмисно немає, щоб не розходились) і **одразу перекриває** `NODE_ENV=test
OPS_LIVE=0`. Кожен тест, який піднімає сервер, робить те саме у себе на
початку — щоб запуск іншим способом теж був безпечним.
